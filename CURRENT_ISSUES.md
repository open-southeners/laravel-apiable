# Current issues (fix/known-gaps round)

## Docs generator only reads PHP attributes, not fluent-style controllers
- **Where**: `src/Documentation/Generator.php` (endpoint/query-param extraction walks `#[FilterQueryParam]`/`#[SortQueryParam]`/etc. reflection attributes only).
- **What**: A controller that configures `JsonApiResponse` fluently (`->allowFilter()`, `->allowing([...])`, …) instead of declaring `#[FilterQueryParam]`-style attributes still gets a documented endpoint (route + method are always picked up), but with an empty query-param list — the generator has no way to see what a fluent call chain allows without executing it. This isn't a regression from this round; it's a structural limitation of attribute-only reflection.
- **Fix**: Needs a runtime-introspection design (e.g. dry-running `JsonApiResponse::using()` against a fake request and reading back `getAllowedFilters()`/`getAllowedSorts()`/etc.), which is a larger feature, not a bug fix. Deferred.

## `AssertableJsonApi::relationship()` breaks `hasSize()`/`at()` for to-many relationships
- **Where**: `src/Testing/AssertableJsonApi.php:204-209` (`relationship()` scopes into `relationships.{name}.data`); `src/Testing/Concerns/HasCollections.php` (`collection()`/`hasSize()`/`at()`, which all call `$this->prop('data')` looking for a further-nested `data` key).
- **What**: For a to-many relationship, `relationships.{name}.data` in the JSON:API document *is already* the array of resource identifier objects — there's no additional `data` key nested inside it. `hasSize()`/`at()` (via the shared `collection()` accessor) look for `$this->prop('data')` at the current scope, which doesn't exist there, so both silently report an empty collection regardless of how many resource identifiers are actually present. The intended usage shown in `.claude/plans/assertable-jsonapi-modernization.md` (Addon E: `$jsonApi->relationship('tags', fn ($tags) => $tags->hasSize(3)->each(...))`) does not work as documented. Found while marking helper-key interaction for `AssertableJsonApi` this round; not something this round's unit owned.
- **Fix**: Either have `relationship()` scope one level higher (`relationships.{name}`, leaving the standard `.data` lookup intact) or teach `collection()` to treat its own scope root as the list when there's no `data` key to descend into. Add a regression test asserting `relationship('tags', fn ($t) => $t->hasSize(N))` against a real to-many relationship.

## `Apiable::$modelResourceTypeMap` is a process-global static with no reset hook
- **Where**: `src/Support/Apiable.php:24` (`protected static $modelResourceTypeMap = [];`), mutated by `modelResourceTypeMap()` (`:139-146`).
- **What**: The map is a static property with no per-test/per-request reset. Any test (or request, under octane/swoole-style persistent workers) that calls `Apiable::modelResourceTypeMap()` mutates global state for everything that runs after it in the same process. `tests/Documentation/QueryParamTest.php` already has to manually save/restore the map around its assertions (`$originalMap = Apiable::getModelResourceTypeMap(); … Apiable::modelResourceTypeMap($originalMap);`) to avoid leaking into other tests — every other test file that touches this map needs the same discipline, and nothing enforces it.
- **Fix**: Add a `TestCase`-level reset (e.g. snapshot/restore in `setUp()`/`tearDown()`) so individual tests don't need to remember to do it themselves, and/or document the persistent-worker caveat for consumers who mutate the map outside of `boot()`.

## `JsonApiPaginator::resolvePageSize()` overrides an explicit page size argument
- **Where**: `src/Http/JsonApiPaginator.php:133-142` (`resolvePageSize()`).
- **What**: `$requestedPageSize` falls back to `responses.pagination.default_size` whenever the `page[size]` request parameter is absent, and the condition `$requestedPageSize && (! $pageSize || $requestedPageSize !== $pageSize)` then overwrites *any* explicitly-passed `$pageSize` argument that doesn't happen to equal the config default — even when the caller passed a specific page size on purpose and the client sent no `page[size]` at all. `JsonApiResponse::simplePaginating(pageSize: …)`/`cursorPaginating(pageSize: …)` (`src/Http/JsonApiResponse.php:195-220`) work around this today by writing straight to `apiable.responses.pagination.default_size` via `config()` rather than relying on the `$pageSize` parameter making it through.
- **Fix**: Redesign the precedence so an explicit `$pageSize` argument always wins over the config default, and `page[size]` (an actual client request) wins over both. Needs a dedicated pass since call sites currently depend on the config-write workaround.

## `Builder::jsonApiPaginate()`'s FastPaginate branch bypasses the pagination strategy dispatch
- **Where**: `src/Builder.php:24-35` (the `class_exists("Hammerstone\FastPaginate\FastPaginate")`/`AaronFrancis\FastPaginate\FastPaginate` branch calls `$this->fastPaginate(...)` and wraps the result directly in a `JsonApiCollection`).
- **What**: This branch never calls `JsonApiPaginator::paginate()`, so it always behaves like length-aware pagination regardless of `responses.pagination.type` — `simplePaginating()`/`cursorPaginating()` have no effect when `hammerstone/fast-paginate` (or its `aaronfrancis` fork) is installed. The optional dependency isn't installed in this repo's dev requirements or the rezero testbed, so this path is untested by either.
- **Fix**: Route the FastPaginate branch through `JsonApiPaginator`'s strategy dispatch (or add FastPaginate-aware `simple`/`cursor` variants), and add coverage once the optional package is available in a test environment.

## `IteratesResultsAfterQuery`: `AbstractPaginator` appends branch has no test coverage
- **Where**: `src/Http/Concerns/IteratesResultsAfterQuery.php:87` (the `elseif ($result instanceof AbstractPaginator)` branch inside `addAppendsToResult()`); the `// TODO: Not really optimised…` comments immediately above it (`:82-83`).
- **What**: This branch is reachable — `JsonApiResponse::serializeResponse()` returns a raw `LengthAwarePaginator`/`Paginator` (not wrapped in `JsonApiCollection`) for the `application/json`/`raw` formats (`src/Http/JsonApiResponse.php:240-245`) — but no test in `tests/Http/JsonApiResponseTest.php` combines appends with a non-JSON:API format, so the branch is currently exercised by nothing. The adjacent `TODO` about the appends post-processing performance (`$result->collection->each(...)` re-walking the whole collection per append) is a pre-existing, still-unaddressed note.
- **Fix**: Add a test combining `forceAppend()`/`appends[]` with `Accept: application/json`, and separately schedule the performance refactor referenced by the `TODO` (not attempted this round).

## `DefaultFilter`/`applyDefaultFilter()` doesn't support the multi-operator pattern `allowFilter()` now has
- **Where**: `src/Http/DefaultFilter.php` (constructor takes `?int $operator`, singular, unlike `AllowedFilter`'s `int|array|null`); `src/Http/Concerns/AllowsFilters.php:106-109` (`applyDefaultFilter()` merges via plain `array_merge_recursive()` instead of the `mergeFilterOperators()`/`operatorPatternsFromFilterEntry()` helpers `allowFilter()` uses).
- **What**: This round's fix for merged same-attribute operators (`AllowedFilter::greaterOrEqualThan('due_at')` + `AllowedFilter::lowerOrEqualThan('due_at')` via `allowFilter()`) only applies to user-supplied filters. Registering the same range shape as a *default* filter (`applyDefaultFilter(DefaultFilter::greaterOrEqualThan(...))` + a second call for `lte`) isn't supported — `DefaultFilter`'s constructor doesn't even accept an operator array, and the merge path would corrupt it the same way `allowFilter()` used to before this round's fix. There's no current use case exercising this in the package or the rezero testbed.
- **Fix**: Port the `mergeFilterOperators()`/multi-operator design from `AllowsFilters::allowFilter()` to `applyDefaultFilter()`/`DefaultFilter` once a real use case needs a default range filter.
